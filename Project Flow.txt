# COMPLETE TECHNICAL ARCHITECTURE REPORT
## LiveKit Voice Agent with RAG
## 1. PROJECT OVERVIEW
### What is the purpose of the project?
This project is a production-grade real-time voice assistant application that enables human users to have spoken conversations with an AI agent. The agent provides:

- Speech-to-Text (STT) transcription of user speech with speaker diarization and recognition
- Large Language Model (LLM) conversation with tool calling capabilities
- Text-to-Speech (TTS) natural voice synthesis
- Document knowledge base search via RAG (Retrieval-Augmented Generation)
- Persistent speaker memory (voice + name association)
- A visual talking avatar (ANAM) synchronized with speech
### What problem does it solve?
It solves the problem of building a low-latency, natural-sounding voice AI interface that:

- Avoids the latency of traditional HTTP-based request/response voice bots
- Recognizes individual speakers by voice and remembers their names across sessions
- Can answer questions from uploaded enterprise/PDF documents with high precision
- Presents a human-looking talking face synchronized with speech output
- Scales across multiple concurrent rooms via a LiveKit worker architecture
### Overall Architecture
Three-tier distributed architecture using LiveKit as the real-time WebRTC backbone:

### High-level flow of the system
1. User visits the React frontend, optionally selects a document, enters a room name and identity
2. Frontend requests a LiveKit JWT token from FastAPI /token endpoint (includes user_id + document_id in metadata)
3. Frontend connects to LiveKit Cloud via LiveKitRoom React component, publishing local microphone audio
4. LiveKit server dispatches a Job to the registered Python agent worker
5. Worker runs entrypoint(ctx) , connects to the room, subscribes to the audio-only stream
6. Speechmatics STT + Silero VAD detect speech and produce diarized transcript per speaker
7. Transcript + conversation history + speaker tags go into custom HuggingFaceLLM (GLM-5.2)
8. LLM may call search_company_documents (Pinecone) or assign_name_2_speaker_ids tools
9. LLM's text response is streamed to Cartesia TTS
10. Cartesia audio is published as a remote audio track in the LiveKit room
11. ANAM avatar publishes a video track of the talking head synced to the audio
12. Frontend subscribes to both tracks: audio plays via RoomAudioRenderer , avatar video renders in a <video> tag
13. Agent statuses ( listening , thinking , speaking , calling_tool ) are sent over the LiveKit data channel and displayed
14. When the last human participant disconnects, the room is deleted via ctx.delete_room()

### Services pinecone_service.py
Class PineconeService with singleton pinecone_service = PineconeService() :

- Lazy init : _initialize() is called on first access to .pc or .assistant property
- Creates/gets Pinecone Assistant named voice-agent-rag with instructions (8 rules: answer from doc only, never guess, etc.)
- Methods :
  - upload_file(file_path, user_id, document_id) → self._assistant.upload_file(file_path, metadata={type:"pdf", user_id, document_id, workspace_id:"default"})

### Worker registration
WorkerOptions(entrypoint_fnc=entrypoint) creates the worker descriptor. The livekit-agents worker:

1. Loads LIVEKIT_URL , LIVEKIT_API_KEY , LIVEKIT_API_SECRET from env
2. Connects to the LiveKit server as a worker
3. Sends a worker registration message declaring it accepts Room job types
4. Blocks waiting for job dispatches
### Job dispatch
When the first participant joins a room (the human user connects via the React frontend), LiveKit:

1. Sees no agent has joined the room yet
2. Creates a RoomJob description referencing the room SID + name
3. Picks an available registered worker
4. Delivers the job over the worker WebSocket
### Worker lifecycle
Per job:

1. Worker allocates a new JobContext ctx
2. Worker spawns a non-main thread
3. User's entrypoint(ctx) runs asynchronously in an asyncio event loop
4. When entrypoint returns OR the job is cancelled by server → ctx shutdown callbacks fire

### ctx.connect()
Signature called: await ctx.connect(auto_subscribe=AutoSubscribe.AUDIO_ONLY) . No video subscribed (keeps bandwidth down). The agent publishes its audio and the avatar publishes video.

### AgentSession creation
AgentSession from livekit.agents orchestrates all AI components. The constructor binds:

- stt : receives raw PCM audio from subscribed mic track
- llm : receives concatenated user+assistant chat items
- tts : receives LLM text chunks, produces audio
- vad : detects speech start/end to drive turn-taking
- preemptive_generation=False : "wait for user to finish speaking before LLM starts" (slower but avoids interrupting mid-sentence)
session.start(agent, room, ...) connects everything together: taps into room audio → VAD → STT → user transcript event → conversation history → LLM chat → tool calling → TTS → publish agent audio track.

### Room connection
Agent participant joins via ctx.connect (above). Avatar joins via avatar.start(session, room) (separate participant identity: "anam-avatar-agent"). Both use the LiveKit SDK credentials.

### Participant events
Registered via decorators:

- @ctx.room.on("participant_connected") → synchronous; parses metadata
- @ctx.room.on("participant_disconnected") → synchronous; creates task for room cleanup
- @ctx.room.on("track_published") → logs
- @ctx.room.on("track_subscribed") → logs
The session object also emits events: user_input_transcribed , conversation_item_added , agent_state_changed

### Audio tracks
- Inbound (user) : Subscribed via AutoSubscribe.AUDIO_ONLY on connect. VAD inspects the track, STT streams audio to Speechmatics cloud.
- Outbound (agent) : Created internally by the session when TTS begins streaming audio bytes. Published as a remote audio track for the frontend RoomAudioRenderer .
### Data channels
Bidirectional reliable data channel is used for agent→frontend status messages. Sent by send_agent_status(status, tool_name?) at worker.py L866-880 using ctx.room.local_participant.publish_data(json.dumps(payload).encode("utf-8"), reliable=True) . Received on frontend via roomContext.on('dataReceived') handler.

### Room lifecycle
1. Frontend connects → room implicitly created by LiveKit if not existing
2. Job dispatched → agent worker accepts → entrypoint(ctx) → ctx.connect() → agent participant joins
3. Human participant → session processes audio back-and-forth
4. participant_disconnected fires → check_and_delete_room() runs; if no humans left, await ctx.delete_room() (not the deprecated api.RoomServiceClient )
5. Also on worker shutdown: ctx.add_shutdown_callback(on_shutdown) triggers same cleanup
### Worker lifecycle (multi-process)
Single worker process can handle multiple rooms concurrently — LiveKit agents framework handles multiplexing. Each room has its own JobContext and entrypoint invocation. The globals stt , known_speakers , participant_metadata are SHARED across jobs (potential race condition — known_speakers is fine because it's written after full load, but participant_metadata being a global dict is a bug if two rooms are active simultaneously).

2. Start detection : Probability crosses start threshold → session emits "speech started" → transitions to listening → publishes status → STT begins feeding Speechmatics
3. End detection : (a) Silero probability below end threshold sustained for N ms AND (b) Smart Turn model analyzes last few seconds + transcript, decides "natural turn end" → session confirms turn is over → only then triggers LLM call (because preemptive_generation=False ; if True, LLM would start as soon as partial transcript is available, but it risks cutting the speaker off mid-thought)

## 13. RAG PIPELINE
### Embedding model
- Provider : Pinecone Assistant internal embedding model. Not explicitly configured; Pinecone applies its default multilingual/e5-equivalent to PDF chunks during upload.
- User-level alternative : The code exposes a retrieve_context() method but that calls Pinecone's assistant.context(...) which performs retrieval but uses Pinecone-chosen embeddings.
- No local embedding code in the repository.
### Chunking
Pinecone Assistant handles chunking during upload_file() based on its internal heuristics (PDF-aware: respects pages, column layout, headings). No chunking parameters exposed in code.

### Vector database
- Managed Pinecone Assistant named voice-agent-rag (stored in Pinecone cloud, not a direct Index)
- Lazy init on first pinecone_service.{pc,assistant} property access
- Creation flow: pc.assistant.describe_assistant(name) → if 404, call pc.assistant.create_assistant(name, instructions=...) with high-precision document bot instructions
- Files scope: Every file upload has workspace_id:"default" , type:"pdf" , user_id , document_id metadata filters
### Metadata
- Per-upload metadata (pinecone_service.upload_file L74-79): {type: "pdf", user_id: str, document_id: UUID, workspace_id: "default"}
- Per-chat filter (used on chat/context): {user_id, document_id} — isolates retrieval to one uploaded document.
- Local registry : storage/documents.json stores {document_id, document_name, uploaded_at}
### Retrieval
Two codepaths exist; only "PASS 1 + PASS 2 with chat" is active :

1. retrieve_context(question, user_id, document_id, top_k=25, snippet_size=1400) → raw retrieved snippets (not actively invoked in chat() , but available if developer chooses to build prompts manually)
2. Two-pass chat() internal flow:
   - Query expansion first (4 variants): [original, lower, stripped, first-6-words, deduped, truncated to 4]
   - Pass 1 : assistant.chat(messages=[{role:"user", content: final_prompt}], temperature=0, include_highlights=True, filter={user_id, document_id}, context_options={top_k=25, snippet_size=1400, queries: expanded_queries})
   - If answer contains any "not found" indicators (via _is_not_found() checking against 6-phrase blacklist):
     - Pass 2 : same call with top_k=40 , snippet_size=800 (more chunks, smaller window to find rare occurrences missed by larger chunks)
   - Answer extracted from response.message.content (most common) with many fallbacks in _extract_answer()
### Ranking
Performed inside Pinecone Assistant's proprietary engine. Multiple queries in context_options is Pinecone's multi-query retrieval mode — all queries execute, their results are de-duplicated and merged by relevance.

### Prompt injection
Three layers of instructions stacked together during Pinecone's answer generation:

1. Assistant stored instructions : set on assistant creation, stored permanently in Pinecone cloud (8 rules: "answer only from uploaded document; never guess; concise, accurate")
2. Per-request user final_prompt : "Answer using uploaded document only. Question: {q}. Rules: 6 rules" — sent in messages[0].content
3. Retrieved document chunks : Pinecone Assistant automatically injects chunks between instructions and the user question (this is hidden behavior, not visible in code)
### Final LLM input
Answer comes from Pinecone hosted LLM inside the Assistant (not the local zai-org/GLM-5.2). The result string is then returned to the worker as a plain tool function return value; the local GLM-5.2 sees it as a tool result item in the conversation history and uses it to craft the final spoken response. So there are TWO LLM calls per RAG tool invocation :

1. Pinecone Assistant internal LLM → final document-grounded answer
2. Worker's HuggingFace GLM-5.2 → combines tool result with conversation context to produce a user-facing utterance.
## 14. TOOL CALLING
### Every tool
Tool 1: assign_name_2_speaker_ids(name: str)

- Registration : Decorated @function_tool in worker.py L1000-1006 ( wrapped_assign_name_2_speaker_ids ), which wraps assign_name_2_speaker_ids L557-752, itself @function_tool decorated originally (L557), then wrapped with tool_wrapper() → status-sending wrapper L883-893 → finally wrapped in outer @function_tool L999-1006 for registration with Agent.
- Purpose : Associates a spoken name with the current speaker's voice fingerprints. Required for conversation continuity across sessions.
- When the LLM decides to call it : SYSTEM_PROMPT explicitly states: "Whenever an unknown speaker introduces themselves: Immediately call assign_name_2_speaker_ids before generating any response." Plus a list of name-introduction phrases: "My name is X, I am X, Call me X, This is X, Myself X".
- Inputs : name: Annotated[str, "The name of the current speaker to remember"]
- Output : Return string confirmation "Got it! I'll remember you as {name}."
- Internal behavior : (1) normalize name (trim, strip punctuation, reject invalid words set). (2) await stt.get_speaker_ids() → fetch voice fingerprints. (3) normalize + dedupe. (4) check for identifier overlap with known speakers. (5) merge-or-create in known_speakers list. (6) save_speakers(SPEAKERS_FILE, updated_speakers) → persistent JSON write.
- Status messages : Sends calling_tool: assign_name_2_speaker_ids before execution, then generating_response after.
Tool 2: search_company_documents(question: str)

- Registration : @function_tool L1008-1015 wraps search_company_documents L762-809, via the same tool_wrapper .
- Purpose : Searches Pinecone uploaded document KB for answer to the user's document question.
- When the LLM decides to call : SYSTEM_PROMPT states "When the user asks about: company documents, uploaded documents, internal policies, manuals, procedures, SOPs, enterprise knowledge, internal documentation → Always use search_company_documents".
- Inputs : question: Annotated[str, "Question regarding uploaded company documents, policies, manuals, procedures, SOPs, internal knowledge base or enterprise documents"]
- Output : Answer string from Pinecone Assistant OR user-facing error string (timeout/HTTP/network/generic error)
- Internal behavior : httpx.AsyncClient(timeout=30.0).POST(settings.RAG_API_URL, json={question, user_id, document_id}) → FastAPI → PineconeService.chat (two-pass). Error handling: 5 explicit exception classes each with distinct user-facing error text (timeout, HTTP status, network request, generic).
- Status messages : "calling_tool search_company_documents" before, "generating_response" after, "tool_failed" on exception.
### Registration
Tools are passed as list to Agent(tools=[...]) constructor (L1020). Agent holds them as FunctionTool instances with Pydantic schema. When HuggingFaceLLMStream initializes, it receives self._tools from the chat call, converts each to OpenAI-format schema with build_strict_openai_schema() .

### Invocation
1. LLM emits chunk with delta.tool_calls
2. Worker code accumulates with partial_tool_calls dict; arguments JSON validation must succeed before emission
3. flush_pending_tool_calls emits FunctionToolCall via _event_ch
4. livekit-agents framework reads events; when finish_reason="tool_calls", invokes each FunctionTool: extracts name, JSON-parses arguments dict, matches to Python signature, awaits the coroutine
5. Result string wrapped in conversation item "tool result"; appended to ChatContext
6. Framework initiates a new LLM chat round automatically so model synthesizes final response from tool return
### How LLM decides
- Tool schema + SYSTEM_PROMPT rules are the only drivers of this decision. LLM (zai-org/GLM-5.2) has native function-calling training.
- Triggering: hf_tool_choice="auto" lets the provider weigh. When SYSTEM_PROMPT explicitly says "Whenever X: Immediately call assign_name_2_speaker_ids before generating any response", LLM reliably emits tool calls on those patterns.
- If tool-calling fails to emit: conversation would continue without tool. SYSTEM_PROMPT's error prevention section adds rules to discourage this.
### Tool execution flow
`LLM stream chunk with delta.tool_calls
   ↓ (in HuggingFaceLLMStream)
partial_tool_calls[index].arguments += func.arguments
   ↓ (per-chunk)
flush_pending_tool_calls() checks JSON validity
   ↓ (when arguments are full JSON)
emit ChatChunk(delta.tool_calls = [FunctionToolCall(name, args, call_id)])
   ↓ (livekit-agents orchestrator)
match name → FunctionTool instance
   ↓
deserialize arguments JSON → Python kwargs
   ↓
await wrapped_assign_name_or_search(kwargs)
   │
   ├─ send_agent_status("calling_tool", name)
   ├─ await func(*args) (actual logic)
   │    ├─ assign_name → stt.get_speaker_ids() + save_speakers()
   │    └─ search_docs → httpx /api/rag/search → PineconeAssistant.chat
   ├─ send_agent_status("generating_response")
   └─ return string
   ↓
append tool result to ChatContext
   ↓
re-invoke HuggingFaceLLM.chat with updated context
   ↓
LLM produces final assistant text → TTS`

### Return values
Both tools return plain strings. The Agent framework appends them as "tool result" items (role=tool or role=system depending on framework) with the corresponding tool_call_id correlation so next LLM call sees the result bound correctly.

## 15. CONVERSATION FLOW: MIC → SPEAKER (single spoken sentence)
1. User speaks into microphone Browser getUserMedia({audio:true}) is called by livekit-client inside LiveKitRoom. Microphone track MediaStreamTrack ready; wrapped as LocalTrack.

2. Local audio capture → encoding livekit-client captures 48kHz float32 samples → converts to OPUS 16kHz mono using built-in encoder → RTP packets.

3. WebRTC transport to LiveKit Cloud ICE connected (STUN/TURN). Packets sent to wss://voice-agent-r9rofr3p.livekit.cloud . LiveKit SFU forwards subscribed tracks.

4. Agent worker receives audio ctx.connect(AutoSubscribe.AUDIO_ONLY) subscribed to all audio. Worker side: AudioFrame events fire on subscribed remote track.

5. Silero VAD detects speech start silero.VAD.load() 's ONNX model silero_vad.onnx processes each frame → speech probability crosses threshold.

6. Session → "listening" state AgentSession internal FSM transitions. agent_state_changed event fired:

`@session.on("agent_state_changed")
def on_agent_state_changed(event):
    new_state = event.new_state
    if new_state in ["listening","speaking","thinking"]:
        asyncio.create_task(send_agent_status(new_state))`

send_agent_status("listening") → local_participant.publish_data('{"type":"agent_status","status":"listening"}') → data channel → Frontend.

7. Speechmatics streaming STT Audio frames passed to Speechmatics STT plugin → WebSocket to Speechmatics Cloud → diarization + partial transcripts streamed back → plugin formats with <speaker>text</speaker> .

8. VAD detects speech end + Smart Turn confirms end-of-turn Silero speech probability drops below threshold for sustained ms AND Smart-Turn model ( smart-turn-v3.1-cpu.onnx ) says "yes this is a turn boundary". Session finalizes the utterance.

9. UserInputTranscribedEvent emitted

`speaker_id = "Ty_Hardin"  (or "S1" if unknown)
transcript  = "<Ty_Hardin>What is our company's remote work policy?</Ty_Hardin>"
is_final    = True`

Logged by on_user_input_transcribed .

10. Session appends user conversation item AgentSession's internal conversation state → new ConversationItem(role="user", text_content="<Ty_Hardin>What is our…</Ty_Hardin>") .

11. ChatContext constructed Includes SYSTEM_PROMPT + all history + latest user item.

12. HuggingFace LLM call llm_instance.chat(chat_ctx, tools=[schema_of_assign, schema_of_search], tool_choice="auto") → returns HuggingFaceLLMStream .

Stream _run() :

- Converts chat_ctx to OpenAI list
- Converts tools to OpenAI JSON schemas
- _generate_once() wraps sync HF call in asyncio.to_thread
13. LLM identifies "company document → must use tool" SYSTEM_PROMPT DOCUMENT SEARCH rules fire → GLM-5.2 decides to call tool.

14. LLM streams delta.tool_calls

`chunk.choices[0].delta.tool_calls[0] = {
    index: 0,
    id: "call_abc",
    function: {name: "search_company_documents", arguments: '{"question":"'}
}`

15. HuggingFaceLLMStream accumulates arguments → eventually valid JSON

`arguments: '{"question":"What is our company remote work policy?"}' → json.loads OK`

flush_pending_tool_calls : emits ChatChunk containing FunctionToolCall("search_company_documents", arguments, "call_abc"). On finish_reason="tool_calls" → forced flush.

16. Tool wrapper executes

`send_agent_status("calling_tool", "search_company_documents")
   → frontend shows 🔧 Please wait, Calling Tool: search_company_documents... + spinner`

17. HTTP to FastAPI /api/rag/search httpx.AsyncClient(timeout=30).POST(http://localhost:8000/api/rag/search, json={question, user_id:"default_user", document_id:"3fa09985-...f1dd5db75e11"})

18. PineconeService.chat() executes two-pass retrieval

- _expand_queries() : 4 query variants
- Pass 1: assistant.chat(messages=[{role:"user", content: final_prompt}], temperature=0, filter={user_id, document_id}, context_options={top_k=25, snippet_size=1400, queries: expanded})
- Pinecone cloud internally: chunk retrieval → re-rank → hosted LLM synthesizes answer from context + instructions
- If "Not found" → Pass 2, top_k=40, snippet_size=800
- _extract_answer() → answer string: "Employees are eligible for up to 2 days per week of remote work with manager approval."
19. Return value → session's ChatContext Tool returns answer string. Orchestrator appends result as ConversationItem(role=tool_result, content=answer, tool_call_id="call_abc").

20. LLM second call (synthesize reply from tool result) Framework re-triggers HuggingFaceLLM.chat() with appended tool result. Now GLM-5.2 sees both user question and tool answer in history → streams delta.content = "According to the document, you can work remotely up to 2 days a week with your manager's approval."

21. ChatChunk text events → session feeds TTS Each ChatChunk's delta.content accumulates by AgentSession; chunks are fed progressively to Cartesia TTS.

22. Cartesia TTS streaming → audio frames Cartesia websocket → audio chunks received by plugin.

23. Agent participant's audio track Session creates LocalAudioTrack for the agent, audio frames pushed into source → LiveKit server.

24. ANAM Avatar video synchronized AvatarSession listens to audio stream → sends audio to ANAM cloud → receives talking-head video → publishes as video track on "anam-avatar-agent" participant.

25. Agent state "speaking" broadcast agent_state_changed event → new_state = speaking → send_agent_status("speaking") data message.

26. Frontend receives audio + video a) RoomAudioRenderer attaches agent audio to WebAudio → browser speakers.
b) ParticipantView's trackSubscribed handler on avatar video track → track.attach(videoRef.current) → <video> element renders synchronized talking head.
c) Status bar shows 🔊 Speaking... + orange wave animation.

27. TTS completes Cartesia stream ends. Track audio buffer drains. Agent transitions speaking → listening. agent_state_changed event fires with old_state=speaking, new_state=listening.

```
if new_state == "listening" and 
old_state == "speaking":
    logger.info(f"[TTS END] Text: '
    {current_agent_response[0]}'")
```
send_agent_status("listening") → frontend returns to 👂 Listening...

Loop is ready for the next user utterance.

### 20.3 assign_name_2_speaker_ids(name: str) -> str — worker.py
- Decorator : @function_tool

- Outputs : Natural language confirmation string (e.g. "Got it! I'll remember you as John." ) OR failure message
- Called by : LLM search_company_documents tool call flow (LiveKit Agent framework invokes it)
- Internal steps :
  1. Normalize name: strip .,!?"' , collapse whitespace, reject INVALID_NAMES set
  2. stt.get_speaker_ids() → raw Speechmatics voice fingerprints
  3. normalize_speaker_ids(raw_speaker_ids) → flat List[str]
  4. Dedupe → dict.fromkeys
  5. Check if speaker identifiers overlap any existing known_speakers[*].speaker_identifiers

     - If overlap with DIFFERENT label → return error: voice already recognized as other person
     - Else label match found → merge ids

  6. Persist: save_speakers(SPEAKERS_FILE, updated_speakers) → writes backend/speakers.json

## 22. ERROR HANDLING
### 22.1 Connection Failures (Frontend ↔ Backend)
- Token request fails : getToken() throws Error('Failed to get token') if response not 2xx.
- Handler at VoiceRoom.jsx L78-81 : catch block logs error, sets status to 'Connection failed' .
- LiveKitRoom connection state : useConnectionState() hook at L255-258 continuously reflects real state (disconnected, connecting, connected, reconnecting). UI shows state in header status indicator.
### 22.2 Worker Failures / Room Cleanup
- Participant disconnect : on_participant_disconnected fires check_and_delete_room() wrapped in asyncio.create_task() at worker.py L932 .
- Room deletion guard : room_deleted nonlocal boolean flag at worker.py L826-851 prevents double-delete (could error).
- ctx.add_shutdown_callback(on_shutdown) at L854-858: fires when worker process itself is gracefully killed; runs check_and_delete_room() one last time.
- Human detection filter : p.identity.startswith("agent-") or identity=="voice-agent-rag" are excluded from "human participants" check — ensures avatar/agent participants don't keep room alive.
### 22.3 LiveKit Disconnects
- Session started with RoomInputOptions(close_on_disconnect=False) at worker.py L1161 — keeps agent session alive briefly across transient participant disconnects.
- ControlBar in frontend provides built-in reconnection handled by livekit-client .
### 22.4 STT Failures (Speechmatics)
- stt.get_speaker_ids() failure inside assign_name_2_speaker_ids at worker.py L627-L632 : caught → returns human-readable "I heard your name is X, but I couldn't save it because speaker identification failed." — does NOT crash the session.
- Empty speaker_ids list → L634-L639: "I heard your name is X, but I couldn't identify your voice yet."
- STT module itself initialized with explicit api_key=settings.SPEECHMATICS_API_KEY at L988; import-time load_dotenv ensures env present.
### 22.5 LLM Failures (HuggingFace Inference)
- 3 retries loop inside HuggingFaceLLMStream._run() worker.py L466-L477 : each retry calls _generate_once() again; after 3 failures, emits hardcoded fallback: via _event_ch.send_nowait() at L479-487 — pipeline stays alive , user just gets an apologetic sentence instead of silent crash.
- Per-chunk parse protection : try/except wraps chunk parsing in _generate_once L399-403 → logs warning, continue next chunk (skips malformed chunk instead of aborting entire stream).
- Event channel close protection in finally: L490-500: attempts both .aclose() / .close() variants; ignores close exceptions.
- HF_TOKEN validation at L1033-1035 pre-session-start: raises ValueError("HF_TOKEN is required") before room session started (hard fail = loud fail, prevents bad sessions).
### 22.6 RAG Tool Failures
- 4 categorized error branches in search_company_documents worker.py L794-809 :
  - httpx.TimeoutException (30s elapsed) → "took too long, try later"
  - httpx.HTTPStatusError (4xx/5xx from backend) → "error searching docs, try later"
  - httpx.RequestError (DNS / connection refused / no route) → "couldn't connect to service"
  - Generic Exception → "something went wrong"
    Tool never throws uncaught; always returns error string. This is critical because the LLM sees the tool return and can comment on it in the second call rather than the whole pipeline exploding.
### 22.7 PineconeService Errors
- PINECONE_API_KEY missing → ValueError inside _initialize() at pinecone_service.py L18-19 .
- _get_or_create_assistant → broad except Exception at L43 wraps create_assistant if describe fails.
- delete_file → L195 warning log if Pinecone fails (tolerates stale delete).
- chat two-pass: any exception → logged with duration then raise to API layer which returns 500 to worker → caught as HTTPStatusError → tool returns user-safe string.
### 22.8 Timeout Logic
- RAG tool HTTP: httpx.AsyncClient(timeout=30.0) — hard 30-second timeout for entire request/response lifecycle.
- LiveKit JWT: expiration is default (6 hours by livekit-api AccessToken default).

## 25. FINAL ARCHITECTURE SUMMARY
The project is a 3-tier real-time voice-RAG assistant built on the LiveKit Agents framework , with WebRTC media transport, managed vector RAG (Pinecone Assistant), streaming HF-hosted LLM tool-calling inference, Speechmatics streaming diarized STT with speaker recognition, Cartesia streaming TTS, Silero local VAD, and an ANAM AI video avatar that lip-syncs to the TTS output.

### Architecture Layers (Bottom-Up Stack)
Layer 1 — Infrastructure / Media Transport (LiveKit Cloud) The entire real-time platform is hosted on a LiveKit Cloud project ( LIVEKIT_URL=wss://voice-agent-r9rofr3p.livekit.cloud ). LiveKit acts as:

- SFU (Selective Forwarding Unit) for WebRTC audio/video tracks: browser mic → LiveKit → Worker (agent), and Worker published audio/avatar-video → LiveKit → browser
- Room registry / lifecycle manager : rooms are created by first join, destroyed by ctx.delete_room() when all humans leave
- Job Dispatcher : when a room is created and needs an agent (determined by LK server logic), the server notifies all registered workers; one worker picks the job and runs entrypoint(ctx)
Layer 2 — FastAPI Backend (HTTP Server, port 8000) Run via uvicorn app.main:app --reload . The FastAPI server provides 4 API routes and 1 health route:

1. POST /token ( token.py ): Input {identity, room_name, metadata} → creates a signed LiveKit JWT (HS256) using livekit.api.AccessToken with VideoGrants(room_join=True, room=room_name) and attaches user_id/document_id as JWT metadata. Returns JWT + LiveKit URL to frontend. This is the ONLY point where the LiveKit API secret is used for user-facing signing.
2. POST /api/rag/search ( rag.py ): HTTP bridge from agent worker (tool) to PineconeService. Accepts {question, user_id, document_id} → calls pinecone_service.chat(...) → returns {answer} .
3. POST /api/documents/upload ( documents.py ): Accepts PDF (multipart/form-data file upload) → saves temp → pinecone_service.upload_file (PDF ingested into Pinecone Assistant managed RAG: PDF parsing → chunking → embedding → vector upsert) → document_registry.save_document appends metadata JSON → temp file deleted.
4. GET /api/documents → Lists documents registered in storage/documents.json.
5. DELETE /api/documents/{document_id} → Deletes from Pinecone and registry.
6. GET /health → returns {"status":"ok"} .
Middleware: CORS ( allow_origins=["*"] — permissive for dev) and HTTP request/response logging middleware at main.py L26-39 .

### End-to-End Execution of One User Utterance (Step-by-Step Micro-Trace)
When user says "My name is Salman" into the microphone:

1. Browser mic captures PCM 48kHz stereo → Opus encoded via WebRTC → LiveKit
2. LiveKit relays to worker; agent subscribed AUDIO_ONLY → receives PCM 16kHz mono
3. Silero VAD classifies → speech_start → VAD_START fires
4. PCM chunks sent to Speechmatics RT WebSocket
5. Speechmatics returns partial then final transcript with S1 tag
6. STT uses known_speakers relabel: if S1 matches existing voiceprints, format becomes <Ty Hardin>My name is Salman</Ty Hardin> . If unknown, <S1>My name is Salman</S1> .
7. SMART_TURN + VAD_END signals end of utterance
8. UserInputTranscribedEvent fires with transcript
9. AgentSession builds ChatContext: system prompt + all prior messages + new user msg with speaker tag
10. Calls HuggingFaceLLM.chat(chat_ctx, tools=[assign_name..., search_docs...], tool_choice="auto")
11. HuggingFaceLLMStream calls HF API with messages[] + OpenAI tools[]
12. zai-org/GLM-5.2 reasons: user said "My name is X", speaker S1 unknown → must call assign_name_2_speaker_ids
13. HF streams tool call JSON chunks; stream class accumulates partial JSON; when valid, emits FunctionToolCall
14. Agent framework invokes assign_name_2_speaker_ids("Salman")
15. Inside tool: stt.get_speaker_ids() → current voiceprints → normalize → check overlap → no match with existing → new SpeakerIdentifier("Salman", [...ids]) → save_speakers(speakers.json) writes to disk → returns "Got it! I'll remember you as Salman."
16. Framework appends tool return to ChatContext
17. Second LLM call with updated context — this time no tool needed; model streams "Nice to meet you, Salman." token by token
18. Each ChatChunk content delta feeds TTS: Cartesia receives text, streams 24kHz PCM chunks back
19. AgentSession publishes PCM as agent audio track → LiveKit → browser subscribed
20. ANAM avatar also receives audio reference from session.start(session, room) hook → animates face publishing video track
21. Browser audio plays; <video> shows animated avatar; on_agent_state_changed sends status "speaking" → frontend shows orange wave animation</video>
22. After last audio frame, state transitions old=speaking→new=listening → log TTS END + data message "listening" → frontend UI shows 👂 Listening... green waves
For a document-related utterance "What is our leave policy?", steps 13-16 call search_company_documents instead, which internally calls FastAPI → PineconeService two-pass chat → returns answer as tool result → step 17 generates final speech.

### Room Lifecycle
- Creation : Auto-created on first user join (LiveKit creates on demand)
- Agent Assignment : LiveKit dispatches ROOM job to first available worker; worker accepts → calls entrypoint
- Conversation : Agent speaks / listens until user disconnects
- Cleanup : On participant_disconnected , if 0 humans (filtered: agent-*, voice-agent-rag, anam-avatar-agent excluded), worker calls ctx.delete_room() , preventing stale room blocking room-name reuse. Worker shutdown additionally runs same check via ctx.add_shutdown_callback(on_shutdown) .
### Key Architectural Constraints Enforced (Per Project Memory)
1. No signal.signal in jobs : Cleanup uses ctx.add_shutdown_callback exclusively — on_shutdown at worker.py L854-858 .
2. All LiveKit event handlers are sync : @ctx.room.on(...) and @session.on(...) handlers are declared with def not async def . Async operations inside use asyncio.create_task(...) .
3. Tool call accumulation with JSON validation : HuggingFaceLLMStream doesn't emit tool calls until json.loads(arguments) succeeds, preventing malformed JSON from reaching agent framework's function execution.
4. Rooms explicitly deleted : ctx.delete_room() in check_and_delete_room with guard room_deleted boolean. This prevents stale LiveKit room state from blocking room name reuse.
5. Room SID access pattern : Uses getattr(ctx.job, "room_sid", None) or getattr(ctx.room, "sid", None) or getattr(ctx.room, "room_sid", None) to avoid logging coroutine objects from property-as-accessor patterns.
6. Participant distinction for cleanup : Remaining participants filtered by NOT (identity.startswith("agent-") OR identity == "voice-agent-rag") to avoid treating agent/avatar as humans.
7. Speaker diarization integration : known_speakers list is persisted via speakers.json; every entrypoint startup reloads it; Speechmatics applies name relabeling so LLM sees <Name>Transcript</Name> which is directly readable by the system prompt rules — no separate speaker lookup pipeline needed in LLM layer.
8. Strict parity with provider format : chat_ctx converts to openai format; tools convert with build_strict_openai_schema — this is why a non-OpenAI provider endpoint works seamlessly with LiveKit's tool calling logic.
